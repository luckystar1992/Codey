# 显示驱动、字体动画与双通道配网 — 技术选型规范

本文是 Codey 固件在「图形渲染」和「设备配置」两大领域的技术选型标准，供后续开发对齐。环境搭建/编译烧录流程见 [`开发的基础方法.md`](./开发的基础方法.md)，本文只讲**选什么、为什么、怎么用、要注意什么**。

结论来自对三个开源参考项目（`opensource/M5StopWatch-UserDemo` 官方 ESP-IDF demo、`opensource/worldcup-2026` 多板 Arduino+LVGL 项目、`opensource/M5Guruguru-Starter` 最小 Arduino 范例）的源码走查，逐条对照 Codey 现状得出。各结论的出处见文末「参考来源对照表」。

---

## 1. 技术选型总览

| 领域 | 选型 | 状态 |
|---|---|---|
| 图形驱动 | **M5GFX**（经 `M5Unified` 板级自动识别） | ✅ 已用（`M5.begin(cfg)`） |
| 字体 / 抗锯齿 | **自产 VLW，8bpp alpha** | ✅ 已用（`scripts/gen_vlw.py`） |
| UI 框架 | **不引入 LVGL，手写 `M5Canvas` 绘制** | ✅ 已用 |
| 动画 | **临界阻尼弹簧插值**（替换写死 lerp 系数） | ✅ 已实现（`codey_spring.h` + `codey_mascot.h`） |
| 配网 A：局域网 Web 配置（AP + captive portal + mDNS） | 沿用现有 `codey_portal.h` 架构 + QR 码 | ✅ 已实现（`drawWifiQr()`，esp-idf 自带 `qrcode.h`，免装库） |

## 2. 显示驱动

### 2.1 选型：M5GFX + M5Unified 自动识别

```cpp
auto cfg = M5.config();
M5.begin(cfg);          // 内部完成 Panel_CO5300 探测、初始化、亮度设置
M5.Display.setRotation(0);
```

**为什么不手写 Panel 类**：`M5StopWatch-UserDemo`（ESP-IDF）里官方是手写 `Panel_CO5300 : public lgfx::Panel_AMOLED` 的，因为 ESP-IDF 用不了 Arduino 生态的板级自动识别。Codey 走 Arduino + `M5Unified`，`M5.begin()` 已经内置了 StopWatch 的面板探测，**没有必要自己重复造轮子**——这是三个参考项目里最省心的路线，继续保持。

### 2.2 硬件参数（供排障 / 手写 fallback 用）

| 项 | 值 |
|---|---|
| 屏幕 | 1.75" 圆形 AMOLED，物理面板 466×466 |
| 控制器 | CO5300，QSPI 接口（`SD0~SD3` 四线 + `SCK`/`CS`） |
| 触摸 | CST820B，I2C |
| 电源/IO 扩展 | M5PM1（PMIC）、M5IOE1（IO expander）—— **必须在显示初始化前**完成 `Wire` 总线上的 PM1/IOE1 `begin()`，否则背光/复位相关引脚状态不对，屏幕可能黑屏（`worldcup-2026` 的 `board::before_display_init()` 明确把这一步放在 `tft.init()` 之前） |

### 2.3 若未来 `M5Unified` 自动识别失效（版本升级踩坑）时的 fallback

`M5StopWatch-UserDemo/main/hal/hal_display.cpp` 里的 `Panel_CO5300` 是**官方权威**的手写初始化序列，关键寄存器：

```cpp
// Tearing Effect Line = 0x1D2 (466)，面板 memory 480x480、可视 466x466（offset_x=6）
static constexpr uint8_t list0[] = {
    0x11, 0 + CMD_INIT_DELAY, 150,   // Sleep out
    0xC4, 1, 0x80,
    0x35, 1, 0x80,
    0x44, 2, 0x01, 0xD2,             // TE line
    0x53, 1, 0x20,
    0x20, 0, 0x36, 1, 0,
    0x51, 1, 0xA0,
    0x29, 0, 0xff, 0xff              // end
};
```

一旦某次 `arduino-cli lib upgrade M5Unified M5GFX` 之后屏幕失灵，先用 `lgfx::Panel_AMOLED` 子类手写这段兜底，而不是排查 M5Unified 自动识别的黑盒逻辑。

### 2.4 注意事项

- **DMA**：`worldcup-2026`（走 `Arduino_GFX_Library`）用的是真 QSPI DMA（`pushImageDMA`）；`M5StopWatch-UserDemo` 官方 LVGL flush 里反而**明确绕开了 M5GFX 的 SIMD/DMA 快速路径**（注释写着 `avoid problematic copy_rgb_fast function`，改用 8KB 分块 `writePixels`），说明 M5GFX 在这块曾经有稳定性问题。Codey 目前走 `M5.Display` 直接绘制（非 LVGL flush 场景），暂无需关心这个坑，但如果以后做整屏 framebuffer/DMA 推流，先查 M5GFX 当前版本这个问题是否已修。
- **PSRAM Sprite**：大面积离屏合成（如 `M5Canvas`）务必 `setPsram(true)`，466×466×2Byte ≈ 435KB，内部 SRAM 放不下。

## 3. 字体与抗锯齿

### 3.1 选型：VLW（LovyanGFX/M5GFX 原生格式），8bpp alpha

```bash
python3 scripts/gen_vlw.py <font.ttf> <size_px> <out.h> <array_name> [--text "0123456789" | --ascii]
```

生成的 `.h` 是字形位图数组，每像素 **0–255 灰度覆盖率**（8bpp alpha），直接烧进固件、`M5.Display`/`M5Canvas` 原生支持，零运行时栅格化开销。

**为什么优于参考项目的方案**：`M5StopWatch-UserDemo` 用 LVGL 字体转换器产出 `--bpp 2`（4 级灰度）；`worldcup-2026` 走 `LV_USE_TINY_TTF`（运行时动态栅格化 TTF，费 CPU/RAM）。Codey 的 8bpp VLW 精度是官方 demo 的 4 倍（256 级 vs 4 级），且是预渲染无运行时开销——**这项已经是三者里最优，不用改**。

### 3.2 新增字体的标准流程

1. 找到目标 TTF，明确要覆盖的字符集（`--ascii` 全 ASCII，或 `--text` 传具体要用到的字符，减小体积——数字表盘这类场景强烈建议用 `--text "0123456789:()"` 之类的窄字符集）。
2. 跑 `gen_vlw.py` 生成 `sketches/codey_dash/fonts/xxx.h`。
3. `#include "fonts/xxx.h"`，`M5.Display.loadFont(xxx)` 或按现有 `codey_theme.h` 里的字体引用方式接入。
4. **不要**为了"多一种字号"而临时用 `setTextSize()` 放大——VLW 是位图字体，整数倍放大会失真，需要放大的字号请重新生成对应 px size 的 VLW。

### 3.3 抗锯齿弧线：M5GFX 没有的東西自己补

M5GFX 没有原生的平滑 `drawArc`。`codey_mascot.h` 里的 `drawArcRange()` 已经实现了逐像素覆盖率计算（边缘按到内外半径的距离算 `cov ∈ [0,1]`，再用 `shade()` 把颜色往背景色混，等效手工 alpha blending）。这是三个参考项目里**质量最高**的 arc 渲染（官方 demo 用 LVGL 内置 arc，抗锯齿精度受限于 LVGL 软件光栅器的默认设置）。

**规范**：以后任何"圆环/弧形进度条"类 UI，复用 `drawArcRange()`，不要退化成分段直线拼接（那样在圆屏上锯齿会非常明显）。

## 4. UI 框架与动画

### 4.1 选型：不引入 LVGL

三个参考项目里两个用了 LVGL9。**Codey 不需要跟进**，原因：

- 466×466 圆屏 + ESP32-S3，全屏动画场景下 LVGL 的 partial-render 缓冲区调优、脏矩形管理本身就是一块不小的复杂度，而 Codey 当前是手写 `M5Canvas` 离屏合成 + 整屏 `pushSprite`，路径更短、更可控。
- LVGL 能提供的是"控件库 + 多 App 生命周期管理"（`mooncake`），这是**产品形态决策**（要不要做成启动器/多应用切换），不是画质或性能问题。如果未来 Codey 真要做"多 App 启动器"，那时候再单独评估要不要接 LVGL + mooncake，不要为了"抗锯齿更好"这类理由引入。

### 4.2 动画：把写死的阻尼系数换成可调弹簧

**现状**（`codey_mascot.h`）：

```cpp
aGlance += (aGlanceTarget - aGlance) * 0.15f;   // 魔法数字，帧率相关，不好调
```

这本质上是一个一阶低通滤波，等效一个隐式的、参数写死的临界阻尼弹簧。官方 demo 用的 `smooth_ui_toolkit` 提供的是**显式弹簧物理**（`springOptions().bounce` / `.visualDuration`），可调回弹和到达时间，观感更可控，而且是纯头文件、不依赖 LVGL，思路可以直接借鉴而不必引入整个库。

**建议实现**（帧率无关的临界阻尼弹簧，基于 `dt` 而非固定系数，可直接抄进新文件如 `codey_spring.h`）：

```cpp
// 临界阻尼弹簧:决定"多久追上目标"(halfLifeMs)而不是每帧瞎调系数。
// dt 单位秒。half-life = 值到达目标一半所需时间,值越小追得越快。
struct Spring1D {
  float value = 0, target = 0;
  float halfLifeMs = 120.0f;

  void set(float v) { value = target = v; }
  void to(float t)  { target = t; }

  void update(float dtMs) {
    float decay = exp2f(-dtMs / halfLifeMs);   // 与帧率无关的指数衰减
    value = target + (value - target) * decay;
  }
};
```

用法：`aGlanceSpring.to(newTarget); aGlanceSpring.update(nowMs - lastMs);`，`halfLifeMs` 就是唯一要调的"手感"参数，比 `*0.15f` 直观且帧率无关（现在的实现如果哪天把 `loop()` 节奏改了，`0.15f` 的观感会跟着变，`Spring1D` 不会）。

**规范**：以后新增的"连续量动画"（表针角度、进度条平滑过渡、mascot 视线偏移……）统一走这一套，不要每处各写一个衰减系数。

## 5. 配网 —— 两条独立通道都要支持

这两条路径**互不依赖**，分别解决不同场景：

| | 路径 A：局域网 Web 配置 | 路径 B：USB 直连配置 |
|---|---|---|
| 触发方式 | 连设备热点 / 同一 WiFi 下访问 `.local` | 数据线连电脑，浏览器/Companion 操作 |
| 依赖 | 无需电脑，手机就能配 | 需要一根 USB 线 |
| 典型场景 | 用户拿到设备第一次配网、没带电脑 | 开发调试、批量产线配置、电脑旁边随手改 |
| 参考实现 | `M5Guruguru-Starter`（AP+mDNS+WebServer+QR）、`M5StopWatch-UserDemo`（AP+DNS captive portal） | `fbiego/ESPConfig`（Web Serial + 自定义帧协议） |

### 5.1 路径 A：AP + captive portal + mDNS

**现状**（`codey_portal.h::wifiConfigPortal()`）已经是三个参考项目里最完整的实现：

```cpp
WiFi.mode(WIFI_AP_STA);
WiFi.softAP("Codey-Setup");           // 开放热点,无密码
DNSServer dns; dns.start(53, "*", apIP);   // 通配符劫持:所有域名都解析到自己
WebServer srv(80);
srv.on("/", portalHandleRoot);
srv.on("/scan", portalHandleScan);
srv.on("/connect", HTTP_POST, portalHandleConnect);
srv.on("/del", portalHandleDel);
srv.onNotFound(...redirect to "/"...);
```

**这套实现比官方 demo 更简洁**：`M5StopWatch-UserDemo/config_ap.cpp` 硬编码了一份 10 条的"各家系统 captive portal 探测 URL"白名单（`/hotspot-detect.html`、`/generate_204` 等）去分别处理；Codey 用**通配符 DNS + 兜底 302 重定向**达到同样效果（任何域名都解析到自己，任何未知路径都跳回 `/`），不需要维护这份易过期的 URL 列表，覆盖面反而更广。**这一点不需要改，甚至可以视为可以反向输出给上游的改进点。**

**mDNS 现状**：`codey_dash.ino:404` 已经 `MDNS.begin("codey-watch")`，但目前只在 **STA 已连上家庭 WiFi 后**用于反向查询 Companion 的主机名（`MDNS.queryHost(...)`），配网门户阶段（AP 模式）并没有对外广播 `.local` 名字——因为 AP 阶段主要靠 captive portal 自动弹窗，mDNS 只是"Mac 桌面浏览器不会自动弹窗时，手动敲网址"的兜底，目前用户走的是"自动弹窗"这条路所以没做。

**待办 / 注意事项**：

1. **无密码开放 AP 的安全窗口**：`WiFi.softAP("Codey-Setup")` 没有密码，配网期间（最长 3 分钟超时）任何人都能连上门户改设备 WiFi。目前用双按键组合退出兜底，可接受，但如果要收紧，加个固定/随机 AP 密码即可，配合下面第 2 点用二维码把密码传达给用户，不影响体验。
2. **补 QR 码配网**（已实现，`codey_portal.h` 的 `drawWifiQr()`）：门户开机画面画 `WIFI:T:nopass;S:Codey-Setup;P:;;` 格式二维码，手机相机扫码直连热点。**没有引入 `ricmoo/QRCode` 库**——实测 `m5stack:esp32` core（基于 esp-idf 3.3.7）自带 `espressif/qrcode` 组件，头文件同样叫 `qrcode.h` 且在编译器默认 include 路径上，会**优先于**任何同名 Arduino 库被解析到，导致 `ricmoo/QRCode` 的 API（`qrcode_initText`/`ECC_LOW`）完全不可见、编译报「未声明」。改用 esp-idf 自带的回调式 API（`esp_qrcode_generate` + `esp_qrcode_get_module`）反而更简单，零外部依赖。**排坑记录**：以后任何 `#include <qrcode.h>` 场景都会撞上这个隐藏的 core 内置头，不要再装 `ricmoo/QRCode`。
3. **mDNS 常驻化**（可选）：如果想要"设备一直挂在家庭 WiFi 上时，随时敲 `codey-watch.local` 进配置页"，把现在只在 AP 阶段起的 `WebServer` 逻辑，在 STA 模式下也常驻一份（复用同一套 handler），`MDNS.begin` 已经在跑，不需要额外基础设施。

### 5.2 路径 B：USB 直连配置（对标但不照搬 `fbiego/ESPConfig`）

**`fbiego/ESPConfig` 的真实架构**（已查过官方仓库确认）：设备端**不跑网页**，只在 USB 串口上跑一个带 CRC-16 校验的自定义帧协议，暴露一张"可配置字段表"（string/int/bool/color/数组/按钮）；`https://fbiego.com/espconfig/` 这个公网页面靠浏览器原生 **Web Serial API**（`navigator.serial.requestPort()`）直接跟 USB 设备通信——这是浏览器沙箱授权的裸串口访问，不走 HTTP，所以能绕开 CORS/混合内容限制，但**仅 Chrome/Edge 桌面版支持，且要求页面跑在 HTTPS 或 `localhost` 安全上下文里**。

**Codey 不需要照搬 Web Serial API 这条路**，因为 Codey 有一个 fbiego 没有的东西：**Companion（本机常驻 Python 进程）已经占着 USB 串口**（`companion/codey/usb_link.py`），而且已经有一套帧协议在跑（`codey_usb.h` ↔ `companion/codey/usb_frames.py`，`0xC0 0xDE | type | len(2) | payload | crc16(2)`）。所以推荐架构是：

```
浏览器(任意浏览器,Safari/Firefox/Chrome 都行)
   │  fetch() / HTTP，走 localhost，无需 HTTPS
   ▼
Companion 本地 HTTP Server（companion/codey/server.py）
   │  已有 config_get_payload / config_post 的路由模式可抄
   ▼
usb_link.py（已经开着的串口连接，复用不用重连）
   │  帧协议：新增 CFG_GET / CFG_SET 帧类型
   ▼
codey_usb.h 的 usbOnFrame() 分支（固件侧）
   │  读写 wifi_store.h / Preferences
   ▼
设备（WiFi 凭证 / 亮度 / 时区……落盘）
```

**为什么这比直接照搬 Web Serial API 更适合 Codey**：
- 不受"仅 Chrome/Edge"限制——任何浏览器打开 Companion 本地页面即可，因为通信是普通 HTTP，不是 Web Serial。
- 不需要额外解决"HTTPS 安全上下文"问题——`http://localhost:PORT` 本身就满足浏览器安全上下文要求，Companion 现成的 `http.server` 已经在监听。
- Companion 已经持有串口连接，浏览器再抢一份 Web Serial 权限反而会跟 Companion 抢占同一个 USB 设备（同一时间只能有一个进程独占串口）。

**待实现清单**（目前 `codey_usb.h` 枚举里没有配置相关帧类型，需要新增，两端保持同步是既有约定）：

1. **固件侧**（`codey_usb.h`）新增帧类型，别跟现有的撞：

   ```cpp
   enum { U_HELLO = 0x01, U_STATE_REQ = 0x10, U_LISTEN = 0x20, U_PCM = 0x21, U_FOCUS = 0x30,
          U_CFG_GET = 0x40, U_CFG_SET = 0x41,             // 新增:读/写设备配置
          U_HELLO_ACK = 0x81, U_STATE = 0x90, U_STT = 0xA0,
          U_CFG_STATE = 0x91, U_CFG_ACK = 0x92 };          // 新增:配置快照 / 写入确认
   ```

   `U_CFG_GET` 无 payload，设备回 `U_CFG_STATE`（JSON：wifi 历史列表**脱敏**、当前 SSID、亮度、时区等，参考 companion 端 `mask_config()` 对密码脱敏的思路，**串口下发给"读取"请求时也不要把密码明文吐出来**，只有 `CFG_SET` 是单向写入不回显）。`U_CFG_SET` payload 是 JSON（如 `{"wifi_ssid":"xxx","wifi_pass":"xxx"}`），设备写入 `wifi_store.h` 后回 `U_CFG_ACK`。

2. **Companion 侧**（`companion/codey/usb_frames.py` 加对应常量；`server.py` 加一对路由，模式抄现成的 `config_get_payload`/`config_post`，只是数据来源从本地配置文件换成"转发一帧到设备、等 ACK/STATE 回包"）。
3. **前端**：`companion/web/admin.html` 加一块"设备 WiFi 配置"，纯 `fetch('/device/wifi', {method:'POST', body: JSON.stringify(...)})`，不涉及任何串口相关的浏览器 API。

**可选的 B2（真·Web Serial，不依赖 Companion 运行）**：如果以后想要"电脑没开 Companion 也能直接拿浏览器配置设备"（比如给不装 Companion 的用户用），才需要真的接 Web Serial API，此时要在前端另外写一份 JS 版帧编解码器（照抄 `usb_frames.py` 的 `crc16`/`encode`/`FrameDecoder` 逻辑），并且只能在 Chrome/Edge 里跑。这是纯前端增量工作，不影响上面 B1 的后端协议设计（同一套 `CFG_GET`/`CFG_SET` 帧类型两条路都能用）。**没有明确需求前不用做**，B1 已经覆盖"开发调试 + 产线配置"的核心场景。
